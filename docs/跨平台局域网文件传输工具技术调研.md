# 跨平台局域网文件传输工具技术调研报告

> 目标：自研一款 AirDrop / LANDrop 级体验的局域网文件传输工具
> 平台：Windows / macOS / iOS / Android　|　场景：同一局域网（含个人热点）　|　差异化重点：桌面右键"发送/分享"集成
> 日期：2026-08

## 1. 背景与目标

现有工具各有短板：AirDrop 体验最好但锁死 Apple 生态；LANDrop 性能指标优秀、全平台，但新版已闭源（官方仓库明确声明 *"temporarily close source"*，开源代码停在 2021-06 的 v0.4.0），且缺少桌面右键分享等系统级集成；LocalSend 开源活跃（Apache-2.0），但其 Windows 集成用的是老式注册表方案且有单实例端口冲突等已知 bug，性能上限也受 Flutter/Dart 技术栈制约。

因此自研目标可定义为：LANDrop 级传输性能（跑满局域网带宽、不压缩、强加密）＋ LocalSend 级开放生态 ＋ 超越两者的系统集成（Windows/macOS 右键即发、移动端系统分享面板接入、信任设备免确认）。

新版 LANDrop 官网宣传的六大特性可直接作为功能基线：跨平台、满速+强加密、热点可用（无移动数据）、无损不压缩、附近分享（不同网络时走 WebRTC）、信任设备（免确认自动接收）。其中前四项属于本次"仅局域网"范围，后两项列为远期扩展。

## 2. 现有方案剖析

### 2.1 LANDrop（重点：老版开源代码可直接参考）

老版源码（[LANDrop/LANDrop](https://github.com/LANDrop/LANDrop)，C++/Qt + libsodium，**BSD-3-Clause**——允许商用/修改，只需保留版权声明）虽停在 v0.4.0，但协议实现完整清晰，是最有价值的参考实现。核心机制如下（已核对源码）：

**设备发现**（`discoveryservice.cpp/h`）：UDP **广播**（非组播），固定端口 **52637**，向 255.255.255.255 及每个网卡的广播地址发 JSON 数据报。报文极简：`{"request": bool, "device_name", "device_type", "port"}`；`request=true` 表示"请报上名来"，收到者回发自己的信息；设置为不可发现时回 `port: 0`。启动时主动广播一次，UI 刷新时再广播请求。

**加密握手**（`crypto.cpp`）：每个会话临时生成 X25519 密钥对，TCP 连接建立后双方**直接互发裸公钥**，`crypto_scalarmult` 算出共享会话密钥。之后所有帧用 **ChaCha20-Poly1305-IETF** AEAD 加密，每帧随机 12 字节 nonce 前置。防中间人手段只有一个：对会话密钥做 BLAKE2b 哈希、取前 8 字节模 10⁶ 得到 **6 位确认码**，两端各自显示，靠人眼比对（这就是 LANDrop 收发时那个 6 位码的由来）。

**传输**（`filetransfersession.cpp`）：单条 TCP 连接，开 `TCP_NODELAY`；帧格式 = 2 字节大端长度 + 密文，因此**单帧上限 64 KB**。文件按帧顺序流式发送，无并行流、无断点续传。

**可借鉴**：整体状态机简洁（HANDSHAKE1 → HANDSHAKE2 → TRANSFER）、6 位确认码交互、发现报文设计。**不要照抄的弱点**：无长期身份密钥（每次都是陌生人，无法实现"信任设备"）、DH 无认证（不比对确认码就可被中间人）、64 KB 帧长限制了单帧效率、随机 nonce 无序列号（无法检测丢帧/重放）、无续传。新版闭源 LANDrop 增加的 WebRTC 附近分享、信任设备等，正是在这套老协议上补的课。

### 2.2 LocalSend（协议开放，生态最大）

Flutter/Dart，Apache-2.0 许可，协议有独立规范仓库（[localsend/protocol](https://github.com/localsend/protocol)）。要点：

**发现**：UDP **组播** `224.0.0.167:53317`，成员上线时组播一条 JSON 公告（alias、version、deviceModel、deviceType、**fingerprint**、port、protocol、download）；收到公告的设备通过 HTTP 回连注册（`POST /api/localsend/v2/register`），组播不可用时退化为对子网逐 IP 的 HTTP 扫描。

**传输**：TCP 53317 上的 **HTTPS REST API**——`prepare-upload`（发送元数据、对方确认、换取 sessionId+token）→ 逐文件 `upload`（binary body）→ `cancel`。每台设备自签 TLS 证书，**fingerprint = 证书哈希**作为设备身份（HTTP 模式下为随机串），支持 PIN。v2 还有反向"下载模式"（收方浏览器直接拉取）。

**Windows 集成现状（引以为戒）**：通过注册表写 `shell` verb 实现"Send to LocalSend"右键项（Win11 下藏在"显示更多选项"二级菜单）；托盘常驻时右键再发会拉起第二个实例、抢 53317 端口失败报 "Address already in use"（[issue #3165](https://github.com/localsend/localsend/issues/3165)）；用户长期要求接入 Win11 一级右键菜单和系统"共享"面板而未实现（[#2641](https://github.com/localsend/localsend/issues/2641)、[#917](https://github.com/localsend/localsend/issues/917)、[#115](https://github.com/localsend/localsend/issues/115)）。这正是你的差异化机会。

## 3. 核心技术方案

### 3.1 设备发现

主方案是 **mDNS/DNS-SD**（注册形如 `_devdrop._tcp.local` 的服务）：四个目标平台都有系统级 API——Apple 的 Bonjour（`NWBrowser`/`NetService`）、Android 的 `NsdManager`、Windows 的 `DnsServiceRegister`（或应用内嵌 mDNS 库）；Rust 侧有 `mdns-sd`、`libmdns` 等纯实现。相比裸 UDP 广播，mDNS 自带服务命名、TXT 元数据、IPv6 与多网卡处理，且被系统缓存。

**iOS 上这是硬约束**：直接收发 UDP 组播/广播需要向 Apple 单独申请 `com.apple.developer.networking.multicast` entitlement，而调用系统 Bonjour API 则不需要——所以移动端发现层必须走系统 API，不能照搬 LANDrop 的裸广播。另外 iOS 14+ 首次联网发现会触发"本地网络"权限弹窗，需在 UI 上做好引导。

兜底链路：其一，UDP 广播/组播公告（LANDrop 的 52637 广播、LocalSend 的 `224.0.0.167:53317` 组播均属此类），应对企业网禁 mDNS；其二，IP/端口直连输入 + **二维码配对**，应对 AP 隔离、访客网络这类广播全灭的环境。发现报文中应携带设备指纹与**协议能力位**，为 §3.4 的双协议自动升级做铺垫。

**发现可靠性设计（LocalSend"搜不到设备"的教训）**。LocalSend 发现不稳有三个根因：其一，公告走 IP 组播，依赖交换机/AP 正确维护 IGMP 组成员，家用 mesh 与企业 Wi-Fi 在跨频段、跨 AP、有线↔无线之间丢组播是常态，而 LANDrop 用子网广播（255.255.255.255 + 各网卡广播地址），链路层默认泛洪，到达率显著更高；其二，LocalSend 以"上线公告 + 缓存"为主，公告包一丢两边互不知情，只能落入逐 IP 的 HTTP 子网扫描（"搜半天"的来源），LANDrop 则是刷新时主动广播 `{"request":true}`、对端立即单播回应的问答式，丢包在下次刷新即自愈；其三，移动端切后台 socket 被挂起、Wi-Fi 漫游/休眠后组播组成员失效未重新 join、VPN 把公告发进隧道、多网卡选错接口，都会制造"重启 App 才搜得到"。

据此自研发现层应做到：mDNS、子网广播、组播**三通道同时收发**（mDNS 虽也是组播，但 AP 普遍为 AirPlay/AirPrint 对 5353 端口专门放行或做 Bonjour 代理，存活率高于自定义组播组）；设备列表按"最近可见时间"维护并设过期；UI 打开与手动刷新时**主动 query** 而非坐等公告；对配对过的设备持久化"指纹 → 上次 IP"，**启动即并行单播探测缓存地址**——广播全灭的网络里常用设备也能秒级上线，这是"打开就看到设备"体验的关键；监听系统网络变化事件（换 Wi-Fi、休眠唤醒、VPN 起停）时重建 socket 并重新加入组播组；最后的兜底扫描用小超时并行 TCP 连接探测，替代逐 IP HTTP 请求。

### 3.2 传输通道与性能工程

| 通道 | 代表 | LAN 吞吐上限 | 优势 | 劣势 |
|---|---|---|---|---|
| HTTPS REST | LocalSend | 中 | 实现快、可被浏览器/curl 访问、生态互通 | 逐文件请求开销、单流、HTTP 栈额外拷贝 |
| 原始 TCP + TLS 1.3 | LANDrop（无 TLS，自制 AEAD 帧） | **高（首选基线）** | 内核栈成熟、低延迟干净链路下吞吐最佳、实现简单 | 多文件并行需自己开多连接；队头阻塞 |
| QUIC | 自研 v2 | 高（Wi-Fi 丢包场景反超 TCP） | 内建 TLS 1.3、多流无队头阻塞、连接迁移（换网不断） | 用户态协议栈 CPU 开销大，干净有线链路吞吐常低于 TCP+TLS |

公开测评的一致结论是：低延迟、无丢包的干净局域网里 **TCP+TLS 吞吐普遍高于 QUIC**（某基准中未调优的 quicly 只跑到 TLS/TCP 的约 40%），而在丢包、高延迟、拥挤 Wi-Fi 下 QUIC 因无队头阻塞与更快握手反超。文件传输的主战场恰好一半是有线/优质 Wi-Fi（TCP 优）、一半是拥挤 Wi-Fi/热点（QUIC 优），所以建议**把传输层做成可插拔**：MVP 用 TCP+TLS 1.3（`rustls`），v2 加 QUIC（`quinn`）并按链路协商。

对标"LANDrop 满速"的工程要点：块大小取 1–4 MiB（LANDrop 的 64 KB 帧上限偏小，靠 C++ 低开销硬扛；自研直接用大块摊薄系统调用与 AEAD 开销）；读盘 → 加密 → 发送三段流水线（双缓冲，避免串行等待）；加密本身不是瓶颈——ChaCha20-Poly1305 与硬件加速的 AES-GCM 单核都在 GB/s 量级，千兆网线速仅 ~117 MB/s、Wi-Fi 6 实测多在 40–90 MB/s，瓶颈通常在网络与磁盘；海量小文件是真正的性能杀手，用打包流（tar 式连续流）或并行流 + 接收端目录预创建解决；逐块 BLAKE3 哈希做完整性与断点续传基准；接收端预分配文件空间（`fallocate`/`F_PREALLOCATE`）减少碎片。

**性能保障方法论："最优"是测出来的，不是选出来的。** 四条纪律：

其一，**定基准上限**：同一路径先跑 iperf3，裸 TCP 吞吐即物理上限，工具目标定为其 90–95%（千兆 ~117 MB/s、2.5GbE ~295 MB/s、Wi-Fi 6 实测 40–90 MB/s）。注意结构性损耗：两台设备挂**同一 AP** 互传，数据过两遍空口（发端→AP→收端），吞吐天然减半——AirDrop 以 AWDL 直连绕开此坑，个人热点（手机即 AP）只有一跳所以反而快，这解释了 LANDrop 热点模式的好体验，也是远期上 Wi-Fi Aware 直连的动机。

其二，**流水线与观测**：读盘 → 加密 → 发送三级流水线、有界队列、缓冲池复用，杜绝每块分配与多余拷贝；AEAD 按块独立（nonce = 块序列号，顺带防重放）则加密可多核并行；BLAKE3 在流水线内顺带完成，绝不二次读盘；接收侧镜像流水线，预分配空间、大块写盘、仅结束时 fsync。**每级安装吞吐计数器**，任何时刻可回答"瓶颈在盘、在 CPU 还是在网"——这是把"最优"变成可验证命题的关键。

其三，**链路自适应**：建连时做 RTT/丢包快速探测并结合接口类型（有线/Wi-Fi）选路——干净链路 TCP+TLS 单/双流即线速；拥挤 Wi-Fi 走 QUIC 多流 + BBR 拥塞控制（quinn 拥塞控制可插拔、含 BBR；"丢包≠拥塞"的假设在 Wi-Fi 上明显优于 CUBIC）；传输中按实测 goodput 动态调整并行流数与块大小。海量小文件（代码目录、相册）必须打包成连续字节流，消掉逐文件请求往返——此项对总耗时的影响常超过所有协议选择之和，也是 LocalSend 逐文件 POST 模式慢的主因。

其四，**回归防退化**：CI 中 localhost + netem 模拟丢包（0/1/5%）×延迟（1/20/50 ms）矩阵自动跑基准；真机矩阵（千兆有线、Wi-Fi 6、手机热点）定期对比 iperf3 上限与 LANDrop/LocalSend 实测值，任何改动造成 >5% 退化即拦截。

### 3.3 安全模型

设计成三层。**身份层**：每台设备持久化一对密钥（实践中直接用自签 TLS 证书，指纹 = 证书哈希，即 LocalSend 的 fingerprint 思路），设备 ID 从此稳定——这是"信任设备"功能的前提，也是老版 LANDrop 最大的缺失（它每次会话都是临时密钥，无法记住任何人）。**信道层**：TLS 1.3，双端各自出示自签证书，校验对方证书哈希是否等于所声称指纹。**配对层**：TOFU（首次见面记指纹）+ 首次配对时双端显示 6 位确认码人工比对（保留 LANDrop 的交互习惯，但确认码必须从认证后的信道密钥派生，才真正防中间人）或输 PIN；配对过的设备进入信任列表后免确认自动接收，即复刻新版 LANDrop 的"信任设备"。

老版 LANDrop 的教训清单：裸 X25519 公钥交换无认证（不比对 6 位码即可被 MITM）、无序列号的随机 nonce AEAD（无法察觉丢帧重放）、无身份持久化。这些在上述模型中全部有解。

### 3.4 协议策略：自研 vs 兼容 LocalSend

| | 兼容 LocalSend v2 | 自研协议 |
|---|---|---|
| 对端生态 | **立即拥有全平台对端**（手机装现成 LocalSend 即可互传，自己的移动端可最后写） | 两端都得自己实现才能用 |
| 实现成本 | 协议规范现成、社区验证充分，就是一组 HTTPS 接口 | 全套自己设计、调试、演进 |
| 性能上限 | 受限：逐文件 POST、单流、无并行/弱续传 | 自由：大块、并行流、QUIC、续传、文件夹语义 |
| 功能自由度 | PIN/指纹有了，但"信任设备自动收"等语义有限 | 完全自主 |

**结论：双协议并行，不二选一。** 核心里抽象出 `Transport`/`Session` 接口：先实现 LocalSend 兼容层（第一周就能和办公室里所有装 LocalSend 的设备互传，移动端开发压力后移）；自研 QUIC 快路径作为第二实现，发现阶段通过能力位协商——两端都是自家客户端时自动升级到快路径，否则回落 LocalSend 协议。这既白嫖了生态，又保住了性能上限。

## 4. 系统集成方案（差异化重点）

### 4.1 Windows：右键"发送"三层实现

第一层，**Win11 一级右键菜单**（体验目标）：实现 `IExplorerCommand` 的 COM DLL，且应用必须具备**包身份**——要么整个应用 MSIX 打包，要么传统安装器 + **sparse package**（空 MSIX 只提供身份，指向外部安装目录，Win10 2004+ 支持）。菜单项可带图标，`EnumCommands` 可动态生成子菜单（直接列出在线设备，"发送到 → MacBook"一步到位）。注意：**部署必须有受信 CA 的代码签名证书**，自签只能本机开发测试。

第二层，**传统注册表 verb**（`HKCR\*\shell\SendWithX\command`）：Win10 一级菜单直接可见，Win11 折叠进"显示更多选项"；10 分钟实现，作为第一层未就绪时的过渡。第三层，**SendTo 快捷方式**（`shell:sendto` 放一个 .lnk）：零代码兜底。锦上添花项：注册 MSIX ShareTarget 后可出现在系统"共享"面板（正是 LocalSend 用户求而未得的 [#2641](https://github.com/localsend/localsend/issues/2641)）。

**单实例架构**（避开 LocalSend 的 [#3165](https://github.com/localsend/localsend/issues/3165) 端口冲突坑）：右键组件永远不自己起服务，只把文件路径经**命名管道**转发给常驻托盘进程，检测不到常驻进程才拉起新实例。

### 4.2 macOS：Share Extension 为主

**Share Extension**（extension point `com.apple.share-services`）是正路：出现在 Finder 右键的"共享"子菜单及全系统分享面板（等同 AirDrop 的入口位置）。必须用 Swift/ObjC 写，独立进程且沙盒化，通过 **App Group 共享容器 + XPC/URL scheme** 把文件句柄交给主 App 发送；用户需在"系统设置 → 扩展"里启用一次，安装后要做引导。

轻量补充：**NSServices**——主 App 的 Info.plist 里声明服务即可出现在右键"服务"子菜单（还能配全局快捷键），零额外进程，M0 阶段十分钟见效。**FinderSync** 虽能把菜单项放到右键一级层级，但它设计上要求声明"受监控目录"（Dropbox 这类同步盘的机制），监控全盘属于 hack，且同样需要用户手动启用扩展，不建议作为主方案。分发要求：Developer ID 签名 + **公证（notarization）**，否则 Gatekeeper 直接拦截。

### 4.3 iOS

发送侧靠 **Share Extension** 接入系统分享面板；注意扩展进程内存上限很低（约 120 MB），大文件不要在扩展内直传，把文件引用写入 App Group 容器后唤起主 App 完成传输。接收侧受平台限制：第三方 App 不可能做到 AirDrop 式后台常驻监听（后台 socket 会被挂起），LocalSend/LANDrop 也一样要求收件时 App 在前台——内部工具场景可接受。加上 §3.1 的本地网络权限与 Bonjour 规避组播 entitlement，iOS 的合规三件套就齐了。

### 4.4 Android

声明 `ACTION_SEND`/`ACTION_SEND_MULTIPLE` intent-filter 即进入系统分享面板；配合 **Direct Share**（ShortcutManager 动态快捷方式）可以把"常发设备"直接顶到分享面板第一排。接收端用**前台服务**挂 mDNS 注册与传输服务器（带常驻通知），存储读写走 SAF/MediaStore。整体是四个平台里最顺的。

## 5. 技术栈选型

一个先决事实可以简化决策：**所有右键/分享集成组件横竖都是原生代码**——Windows 的 COM DLL（C++ 或 Rust `windows` crate）、macOS/iOS 的 Share Extension（Swift）、Android 的 intent（Kotlin），任何 UI 框架都替你写不了。所以框架之争只关乎"主程序 + 传输核心"。

| | Rust 核心 + 原生壳 | Flutter 全平台 | Kotlin Multiplatform | C++/Qt（LANDrop 路线） |
|---|---|---|---|---|
| 性能上限 | **最高**（tokio/quinn/rustls，零 GC） | 中（Dart HTTP 栈与跨 isolate 拷贝需精心设计才能跑满千兆） | 高（JVM/Native 混合） | 最高 |
| 桌面右键/托盘集成 | **原生，无缝** | 需平台通道插件粘合 | 桌面偏弱 | 尚可，但扩展仍需原生 |
| 一套代码复用度 | 核心 100%，UI 每平台一份 | **UI + 逻辑近 100%** | 逻辑共享，UI 按平台 | 高，但移动端 Qt 体验差 |
| 单人出全平台速度 | 慢（4 套壳） | **最快**（LocalSend 单人先例） | 中 | 慢，移动端痛苦 |
| 生态先例 | 1Password/Bitwarden 式"Rust 核心多壳" | LocalSend | 少 | LANDrop（已弃开源） |

**推荐（质量线）：Rust 核心 + 原生壳。** 核心 crate 承载发现（`mdns-sd`）、双协议传输（`hyper`/`quinn` + `rustls`）、信任库与传输引擎，经 **UniFFI** 生成 Swift/Kotlin 绑定；macOS/iOS 壳用 SwiftUI（Share Extension 反正要写 Swift），Android 壳用 Compose，Windows 壳用 Tauri 2 或 WinUI（Tauri 的 Rust 后端与核心零成本对接，托盘/自启/单实例插件齐全）。理由：你的两个核心诉求——LANDrop 级性能上限、深度系统集成——恰好都是这条线的强项，且核心一旦写好，四个壳都很薄。

**替代（速度线）：Flutter。** 若首要目标是"三个月内全平台都能用"，LocalSend 已验证此路线可行，集成缺口用平台通道补，后期性能不够再用 `flutter_rust_bridge` 把传输核心换成 Rust。两条线的原生集成代码完全可复用，切换成本可控。

**附注（结合 WireHop 现状的修正）**：本章推荐写于独立选型视角。既然 WireHop 已基于 LANDrop 0.4 的 C++/Qt 代码稳定运行，并完成了 macOS Services / Share Extension 集成，桌面端不应推翻重写。正确路径是**协议规范先行**：为现有实现补上协议版本字段与能力协商（沿用 ACK 的"增量兼容"手法），把 `PROTOCOL.md` + 黄金测试向量当作真正的跨平台资产；移动端以原生壳（Swift/Kotlin）按规范实现协议，而非上 Qt 移动端（LGPL 静态链接义务与移动体验都不划算）。Rust 核心保留为远期选项——若 QUIC 快路径立项，可以独立库形式增量接入，仍不需要重写。

## 6. 推荐架构与落地路线

```
┌────────────── 各平台壳（薄） ──────────────┐
│ Win: 托盘 + IExplorerCommand DLL ──┐        │
│ macOS: 菜单栏 + Share Ext ─────────┤命名管道│
│ iOS: App + Share Ext ──────────────┤/ XPC   │
│ Android: App + SEND intent ────────┘        │
└───────────────────┬────────────────────────┘
              UniFFI 绑定
┌───────────────────▼────────────────────────┐
│         core（Rust，单一 crate）            │
│ 发现: mdns-sd + UDP 公告 + 二维码直连        │
│ 传输: LocalSend v2 兼容层 │ QUIC 快路径      │
│ 安全: 证书身份 + TOFU 信任库 + SAS           │
│ 引擎: 流水线 IO / BLAKE3 / 断点续传          │
└─────────────────────────────────────────────┘
```

| 里程碑 | 内容 | 产出 |
|---|---|---|
| **M0（1–2 周）** | Rust 核心 + CLI + LocalSend 协议兼容；Windows 注册表 verb + SendTo；macOS NSServices | **立即自用**：桌面右键发文件到手机上现成的 LocalSend App |
| M1 | 托盘/菜单栏常驻 + 单实例管道；Win11 IExplorerCommand + MSIX 签名；macOS Share Extension + 公证 | 右键体验达到设计目标 |
| M2 | QUIC 快路径 + 断点续传 + 信任设备（免确认） | 性能与体验超越 LANDrop |
| M3 | iOS/Android 原生壳（Share Extension / SEND intent） | 全平台自有客户端 |
| M4（远期） | Wi-Fi Aware 无路由直连（iOS 26 已开放该框架且可与 Android 互通，是第三方逼近 AirDrop 离线体验的官方通道）；WebRTC 跨网传输（对标新版 LANDrop"附近分享"） | 超出局域网限制 |

## 7. 风险与坑清单

- **Windows 签名成本**：Win11 一级右键菜单（MSIX/sparse package）必须受信 CA 代码签名证书，个人 OV 证书每年数百到上千元；纯自用可自签 + 本机信任根，分发则绕不开。
- **iOS 平台限制**：后台常驻接收不可行（收件须前台）；裸组播需专门 entitlement（走 Bonjour API 规避）；Share Extension 内存上限，大文件必须转交主 App。
- **macOS 分发摩擦**：不公证必被 Gatekeeper 拦；Share/FinderSync 扩展默认不启用，需首启引导用户去系统设置勾选。
- **网络环境兜底**：企业网常禁 mDNS/广播，访客网络常开 AP 隔离——二维码/IP 直连不是可选项而是必备项；Windows 防火墙、macOS 应用防火墙首次监听都会弹窗，需引导。
- **多网卡与 IPv6**：虚拟网卡（Docker/VPN）会污染发现结果与选路，需按接口过滤并优先物理网卡；IPv6 link-local 地址要带 scope id。
- **休眠断传**：笔记本合盖即断，断点续传应进 M2 而非"以后再说"。
- **海量小文件**：单文件顺序 POST 会慢一个数量级，自研快路径要内建打包流/并行流。
- **许可合规**：参考/复用 LANDrop v0.4 代码须保留 BSD-3-Clause 版权声明；LocalSend 为 Apache-2.0（注意其协议规范本身可自由实现，兼容实现不构成派生）。
